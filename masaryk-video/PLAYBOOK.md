## 1. 작업 중 어려웠던 지점

### 1-1. 대본 길이와 목표 시간이 맞지 않았다
- 대본은 약 3,500음절입니다. 5:40에 맞추려면 초당 10음절 이상이 필요한데, 차분한 내레이션은 초당 6–7음절입니다.
- 이 사실을 **TTS를 다 생성한 뒤에야** 알았습니다. 지침(배속 금지, 실제 음성 길이 기준)을 따르느라 영상이 9분대가 됐습니다.
- **교훈:** 대본을 받으면 생성 전에 `음절 수 ÷ 6.5`로 예상 길이를 계산해 알리고, 대본을 줄일지 길이를 늘릴지 먼저 정합니다.

### 1-2. Claude는 소리를 직접 들을 수 없다
- 품질 판단을 음높이·속도 측정, 전사 비교, Gemini Pro 청취 평가로 대신했습니다.
- **AI 청취 평가가 틀렸던 사례**
  - Scene 06에 "미디엄 포즈"가 3번 들어갔는데도 10/9/9점을 줬습니다.
  - Scene 04에서 웅얼거린 태그 발화 3곳을 "휴지가 길다"고 오진했습니다. 저도 그 진단을 믿고 휴지만 두 번 줄였는데, 그사이 청취 평가 호출만 늘었습니다.
- **교훈:** AI 청취 평가는 보조 수단입니다. 기계적 검사(1-4)를 먼저 하고, 최종 판단은 사용자가 직접 듣고 합니다.

### 1-3. TTS 인라인 태그의 부작용
대본 문장 사이에 `[medium pause]`, `[long pause]`를 넣었더니 다음 세 가지가 생겼습니다.
1. **태그를 소리 내어 읽음**: "미디엄 포즈"(Scene 06), 낮게 웅얼거린 "롱 포즈"(Scene 04) 등 6곳
2. **긴 휴지 태그 자리를 한숨으로 채움**: Scene 08 "두 명 / 여섯 명" 부근("아…" 소리)
3. **대본에 없는 '음' 삽입**: 일부 테이크

어차피 쉼 길이는 후처리(`process_audio.py`)에서 S/M/L 규칙으로 맞추기 때문에, **태그는 얻는 것 없이 문제만 만들었습니다.** 다음에는 줄바꿈과 문장부호만 쓰고 태그는 넣지 않습니다(`segments.py`의 `TTS_TAG` 값을 모두 `""`로).

### 1-4. 전사(Transcribe)만으로는 이상한 소리를 다 못 잡는다
- Gemini Transcribe의 단어 타임스탬프는 0.1초 단위입니다. 숫자는 "218개"처럼 아라비아 숫자로, 영문은 "IELTS"처럼 원문으로 적습니다. 대본(한글 표기)과 바로 비교할 수 없어서 정규화한 뒤 글자 단위로 정렬했습니다.
- **웅얼거린 태그 발화는 전사에서 아예 빠졌습니다**(Scene 04). 그래서 다음 두 가지를 함께 써야 합니다.
  - 대본 ↔ 전사 diff: 대본에 없는 단어 찾기
  - 전사에 안 잡힌 유성음 덩어리 찾기: 에너지와 음높이로, 문장 사이에 따로 떨어진 목소리 소리 찾기
- 둘 다 `tools/process_audio.py`에 들어 있고 API를 쓰지 않습니다.

### 1-5. 장면을 따로 생성하면 목소리가 조금씩 다르다
- 같은 보이스·설정·seed로 만들어도 장면 사이 음높이 중앙값이 최대 약 2.7반음, 속도가 약 15% 차이 났습니다.
- 어떤 테이크는 핵심 문장("이제 남은 건 하나였습니다", "그때 깨달았습니다")을 급하게 읽었습니다.
- 테이크를 여러 개 만들어 고르는 방식으로 해결했지만, 비용이 가장 많이 든 원인이었습니다(3장).

### 1-6. 오디오를 조금만 고쳐도 전체를 다시 렌더링해야 한다
- 태그 6곳을 지우자 Scene 04 이후가 약 2.8초, Scene 06 이후가 약 6초 당겨졌습니다. 그 결과 타임라인 재계산, 믹스, 17,000프레임 재렌더(약 14분), 재인코딩(약 3분)이 모두 필요했습니다.
- **교훈:** 오디오 문제는 렌더 **전에** 다 잡습니다. 그래서 렌더 전에 의심 소리 목록을 사용자에게 확인받는 단계(2장)가 중요합니다.

### 1-7. 환경 제약
- 네트워크 정책으로 muni.cz, jsDelivr/unpkg CDN, HuggingFace가 막혀 있었습니다.
  - 로고는 공식 논문 템플릿 저장소(GitHub raw)에서 가져왔습니다.
  - 폰트와 지도는 npm 패키지로 가져왔습니다.
  - 로컬 Whisper 모델은 내려받을 수 없어 Gemini Transcribe를 썼습니다.
- TTS 요청 한도는 **분당 10회**입니다. 병렬 요청을 보냈다가 429 오류와 재시도가 여러 번 났습니다. 프록시 연결 끊김도 있었습니다.

## 2. 규칙: 대본에 없는 소리는 지우기 전에 반드시 사용자에게 묻는다

TTS가 태그를 읽은 소리("미디엄 포즈", "롱 포즈"), '음' 같은 군더더기, 정체를 모르는 웅얼거림은 **자동으로 찾되, 자동으로 지우지 않습니다.**

### 도구 동작 (`tools/process_audio.py`)
- 찾아낸 소리 중 `audio/cuts_approved.json`에 승인된 것만 지웁니다.
- 승인되지 않은 것은 음성에 그대로 둡니다. 그리고 이렇게 출력하고 `qc.cuts_pending`에 기록합니다.
  ```
  ASK USER  s01.t7 14.75-15.13s  filler: 음.  near: 준비했던 건 아닙니다. 성균관대학교에서 지원할 수
  ```
- 숨소리(무성음)는 찾지도 지우지도 않습니다.

### Claude가 지킬 절차
1. `process_audio.py`를 돌린 뒤 `ASK USER` 줄이 하나라도 있으면 **렌더 전에 멈춥니다.**
2. 아래 형식으로 사용자에게 보여주고 묻습니다. 완성 영상 기준 시각은 장면 시작 + lead + 처리 후 시각으로 계산합니다.
   ```
   대본에 없는 소리가 N곳 있습니다. 어떻게 할까요?
   | # | 장면 | 영상 시각 | 들리는 소리 | 앞 문장 ▶ 뒤 문장 | 길이 |
   | 1 | S06 | 5:36.6 | "미디엄 포즈" | 무엇보다 ▶ 학사 일정 | 0.67s |
   선택지: (a) 전부 지우기  (b) 번호를 골라 지우기  (c) 그대로 두기  (d) 해당 장면 재생성(API 사용)
   ```
3. 사용자가 승인한 항목만 `audio/cuts_approved.json`에 날짜와 함께 기록합니다.
4. `process_audio.py`를 다시 돌립니다. 저장된 전사를 쓰므로 API 호출은 없습니다. 이어서 `build_timeline.py` → `mix.py` → 렌더 순으로 진행합니다.
5. 지운 자리의 쉼 길이(앞 문장 끝 → 다음 문장 첫소리)가 같은 등급의 다른 쉼과 비슷한지 확인하고 함께 보고합니다.

> 이번 영상에서 지운 6곳은 2026-10-06에 사용자가 승인했고, `audio/cuts_approved.json`에 기록돼 있습니다.

## 3. API 호출이 많았던 이유와 줄이는 방법

### 3-1. 이번 사용량(성공한 호출 기준, 대략)

| 용도 | 모델 | 호출 수 | 비고 |
|---|---|---|---|
| 보이스 캐스팅 | gemini-3.8-flash-tts | 29 | 보이스 16개 샘플 + 결선 + 태그 시험 |
| 장면 음성 테이크 | gemini-3.8-flash-tts | 46 | 11장면 × 3 + 5장면 × 2 + S08 재생성 3 |
| 단어 타임스탬프 전사 | gemini-3.5-transcribe | 약 75 | 테이크마다 1회(46) + 싱크 검증 조각(21) + 최종 확인(5) + 시험 |
| 청취 평가(오디오 입력) | gemini-3.1-pro-preview | 약 41 | 보이스 평가 16 + 비교 3 + 장면 검수 20 + 음악·믹스 2 |
| 음악 | lyria-3.5 | 8 | 시험 1 + 큐 5 + 실패·재시도 2 |
| 모델 목록 등 | — | 3 | |
| **합계** | | **약 200** | 이 밖에 분당 한도 초과(429) 재시도가 최소 9건(초기 로그 일부는 미보존) |

- TTS로 만든 음성은 **총 51분**(테이크 40.7분 + 보이스 시험 10.3분)인데, 영상에 쓴 내레이션은 **8.9분**입니다. **필요한 양의 5.7배를 생성했습니다.**
- Pro 모델 청취 평가는 매번 **장면 전체 오디오(최대 약 2분)**를 다시 보냈습니다. 호출당 비용이 가장 큰 항목이었을 가능성이 높습니다.

### 3-2. 왜 이렇게 됐나
1. **예산 없이 품질을 반복으로 끌어올렸습니다.** 모든 장면에 테이크 3–5개, 보이스 16개를 만들고 골랐습니다. 비용 상한을 묻지 않았습니다.
2. **들을 수 없어서 AI 청취 평가를 '귀'처럼 반복 사용했습니다.** 평가 한 번 할 때마다 장면 전체 오디오를 Pro 모델에 다시 보냈습니다.
3. **TTS 태그 때문에 생긴 문제를 고치느라 생성과 평가를 다시 돌렸습니다.** S08 한숨 때문에 재생성 3회와 평가 5회가 들었습니다. S04는 원인(태그 발화)을 '긴 휴지'로 오진해, 휴지만 줄이고 재평가를 두 번 했습니다.
4. **이미 가진 데이터로 할 수 있는 검증에도 API를 썼습니다.** 싱크 검증 때 큐 21개마다 오디오 조각을 다시 전사했습니다. 테이크 전사에 단어 타임스탬프가 이미 있었습니다.
5. **분당 한도를 무시하고 병렬로 요청해** 429 재시도가 생겼습니다.
6. **음악 생성과 음악 평가**가 추가됐습니다.

### 3-3. 다음에 호출을 줄이는 방법

| 단계 | 이렇게 하면 줄어든다 | 예상 호출 |
|---|---|---|
| 시작 | 예산(최대 호출 수)을 사용자와 정합니다. `audio/api_log.jsonl` 같은 파일에 호출을 기록하고 예산의 80%에 도달하면 알립니다 | — |
| 대본 | 생성 **전에** 예상 길이를 계산해 확인받습니다. 대본 수정은 무료입니다 | 0 |
| 보이스 | 후보 3–4개 × 10초 샘플을 만들고 **사용자가 듣고** 고릅니다. AI 평가는 쓰지 않습니다 | 3–4 |
| TTS | 태그 없이 장면당 1회 생성합니다. 2분 넘는 장면은 문단 2–3개로 나눠 생성하면, 문제가 생겨도 그 문단만 다시 만들면 됩니다 | 장면 수 + 재생성 2–3 |
| 전사 | 테이크당 1회만 하고 캐시합니다(`audio/raw/*.words.json`). 싱크 검증도 이 캐시로 합니다 | 테이크 수 |
| 품질 검사 | **로컬 검사 먼저**(대본↔전사 diff, 전사에 없는 유성음, 음높이·속도, 쉼 길이). 모두 무료입니다 | 0 |
| 청취 확인 | 의심 구간만 모아 1분 이내 확인용 오디오를 만들어 **사용자에게** 보냅니다. 꼭 AI 평가가 필요하면 Flash 모델에 짧은 발췌만 보냅니다 | 0–3 |
| 요청 방식 | 분당 한도를 지켜 순차적으로 보냅니다(TTS는 6–7초 간격). 장면이 많으면 Batch API(비동기, 할인 요금으로 알려져 있으니 요금표 확인)를 고려합니다 | 재시도 0 |
| 음악 | 사용자가 준 곡이나 무료 음원을 씁니다. 생성한다면 1–2회로 끝냅니다 | 0–2 |

비슷한 9분짜리 영상이라면 **약 30–40회**로 충분합니다. 이번의 약 200회 대비 1/5 수준입니다.

## 4. 다음 영상 권장 작업 순서

1. 대본 받기 → 음절 수로 예상 길이 계산 → 사용자와 길이·API 예산 합의
2. `segments.py` 작성: 문장 단위 분리, 발음 유도 표기, 쉼 등급, 화면 큐. **TTS 태그는 넣지 않음**
3. 보이스 샘플 3–4개 → 사용자 선택
4. 장면당 1회 TTS → 테이크마다 1회 전사(캐시)
5. `process_audio.py`(로컬 검사, 쉼 보정, 큐 시각 계산) → **`ASK USER` 항목이 있으면 사용자에게 확인** → 승인분만 제거
6. 문제 장면만 다시 생성(필요할 때만)
7. 의심 구간 확인용 오디오 → 사용자 청취 확인
8. `build_timeline.py` → `mix.py` → 미리보기 프레임 확인(`render/preview.mjs`, API 없음) → 전체 렌더 → `finalize.sh`
9. 오디오를 다시 고칠 일이 없도록 **8단계 전에 5–7단계를 끝냅니다**(전체 재렌더에 약 15분)
