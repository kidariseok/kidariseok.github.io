# Recruiter Review Loop (채용 담당자 관점 점검 시퀀스)

포트폴리오를 고칠 때마다 **채용 담당자 페르소나 서브에이전트**가 실제 화면을 보고 점검하고, 그 결과를 반영해 다시 점검받는 반복 과정입니다.
한 번의 수정으로 끝내지 않고 `점검 → 종합 → 수정 → 재점검` 을 돌려, 이전 라운드의 지적이 실제로 해결됐는지를 다음 라운드가 확인합니다.

- 페르소나 정의: `.claude/agents/recruiter-*.md` (Claude Code 가 서브에이전트로 불러 씀)
- 화면 캡처: `tools/review-capture.mjs` (Playwright 필요 · 사이트에는 영향 없음)
- 라운드 기록: [docs/review-log/](review-log/) — 라운드마다 페르소나별 보고와 종합본

## 1. 시퀀스

```text
0. 캡처      python3 -m http.server 8000  →  node tools/review-capture.mjs <폴더>
             (메인 'SELECTED WORK' 화면 · 대표 활동 상세의 첫 두 화면, KO/EN · 1440/390px, 본문 텍스트)
1. 점검      페르소나 3명을 병렬로 실행. 각자 같은 캡처를 보고 2장의 형식으로 보고
2. 종합      메인 에이전트가 세 보고를 합쳐 중복을 묶고 우선순위(P0–P2)를 정함
             · 사실이 필요한 제안(숫자 추가 등)은 '작성자 확인 필요'로 분리 — 만들어 넣지 않음
             · 저장소 규칙(CLAUDE.md)과 충돌하는 제안은 이유를 적고 보류
3. 수정      P0 → P1 순으로 반영. KO/EN 같은 커밋. node tools/check-content.mjs
4. 재점검    다음 라운드는 '이전 종합본'을 함께 받아 항목별로 해결 / 일부 / 미해결 / 악화를 판정
5. 종료 조건 P0 가 0개이고, 대표 활동 스코어카드의 '첫 화면 식별'이 모두 ○ 또는 △(사유 있음)일 때
             · 최대 3라운드. 남은 항목은 종합본의 '보류' 표로 넘김
```

## 2. 보고 형식 (모든 페르소나 공통)

### 2.1 10초 요약

캡처만 훑어보고 "이 사람은 ___ 한 사람이다" 를 한 문장으로 씁니다. 쓸 수 없으면 왜 쓸 수 없는지 적습니다.

### 2.2 스코어카드

대표 활동마다 **스크롤하지 않은 첫 화면**(`*_1.png`)만 보고 판정합니다. ○ 바로 보임 · △ 찾으면 보임/모호함 · ✕ 첫 화면에 없음.

| 활동 | 문제·목적 | 내 역할 | 핵심 판단 | 결과(종류가 맞게) | 팀/개인 구분 | 숫자 맥락(분모·범위) |
| --- | --- | --- | --- | --- | --- | --- |

그 밖에 5점 척도: 훑어보기 쉬움 · 기획 역량의 증거 · 신뢰성(과장 없음) · 일관성 · 모바일 가독성.

### 2.3 발견 사항

| ID | 심각도 | 위치 (파일명 · 화면 구역) | 관찰한 것 | 채용 담당자에게 왜 문제인가 | 제안 | 유형 |
| --- | --- | --- | --- | --- | --- | --- |

- 심각도: **P0** 서류 단계에서 오해·감점 소지 / **P1** 이해가 느려짐 / **P2** 다듬기
- 유형: 내용 · 구조 · 시각 · 사실확인 · 번역
- 새 숫자 · 성과를 제안할 때는 반드시 `작성자 확인 필요` 를 붙입니다. 사이트에 없는 사실을 지어내지 않습니다.

### 2.4 유지할 것

지금 잘 되어 있어 고치다 망가지면 안 되는 것 3–5개.

## 4. 다시 돌리는 법 (다음 작업자용)

Claude Code 에서:

```text
docs/RECRUITER_REVIEW.md 의 시퀀스대로 라운드 N 을 돌려줘.
이전 종합본은 docs/review-log/round-(N-1)-synthesis.md
```

캡처 폴더는 저장소 밖(임시 폴더)에 두고, 보고서와 종합본만 `docs/review-log/` 에 남깁니다.

**반복하며 배운 것**

- 세 페르소나가 **같은 문제를 서로 다른 이유로** 짚을 때(예: GDG '300명' — 인사팀은 '확인 안 되는 숫자', PM 리드는 '운영 vs 지원', 외국계는 '카드가 상세보다 큼') 가장 확실한 수정 대상이었다.
- 수정이 회귀를 만든다. Round 1 에서 세 명 모두 '접기'가 핵심(AI가 하는 일, 본인 기여)까지 숨긴 것을 찾아냈다 → 다음 라운드는 반드시 **이전 수정의 부작용**을 따로 보게 할 것.
- 페르소나는 사실을 지어내지 않고 질문으로 남긴다. 그 질문 목록(각 종합본 4장)이 다음 개선의 재료다.
